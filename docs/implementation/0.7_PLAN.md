# Home Agent 0.7 Implementation Plan

**Status:** Proposed implementation scope  
**Baseline:** 0.6.2  
**Theme:** Permanent local data foundation

## Goal
Upgrade 0.6.2 to 0.7 without data loss while establishing the permanent identity, migration and persistence foundation required by the frozen architecture.

Success means existing rooms, relationships and notes still work after migration and the backend can represent permanent IDs plus the initial Source/IngestOccurrence/InboxItem processing foundation.

## In scope
1. Explicit schema versioning and deterministic startup migrations.
2. Opaque permanent UUIDv7 IDs for migrated domain objects.
3. Existing textual IDs retained only as legacy mappings/attributes.
4. Foundational persistence for Source, IngestOccurrence and InboxItem.
5. Durable processing-state fields/invariants sufficient for later Inbox processing.
6. Domain mutation + required audit/history atomic for write paths touched by 0.7.
7. Preserve existing 0.6.2 room browsing, relations and additive note behavior.
8. Deterministic diagnostics/verification for migration integrity.
9. Keep v013/YAML bootstrap as historical/bootstrap source, not runtime truth.

## Out of scope
OpenAI/API integration, Drive Inbox synchronization, Drive archive/backup implementation, automatic source classification, Home Assistant entity integration, broad UI redesign, full edit/delete workflows and production retention/encryption policy.

## Migration requirements
Migration is idempotent and transactional where possible. Restarting after interruption must not duplicate entities or regenerate permanent IDs.

Every migrated persistent object receives one permanent internal ID. Existing textual IDs remain only as legacy mappings where needed to resolve current data/relations.

Existing notes and audit/history are preserved. Existing user-visible rooms or relations must not disappear because identity representation changes.

A failed migration must fail safely, remain diagnosable/retryable and never silently activate partial state.

## Persistence contract
0.7 establishes storage for schema metadata/version, permanent identity + legacy mapping, Source, IngestOccurrence, InboxItem, required processing state and audit/history for touched write paths.

Implementation may remain SQLite-specific internally, but domain identity does not depend on SQLite row IDs. No AI or Drive behavior is required merely because these records exist.

## UUID requirement
Target format is UUIDv7. If runtime Python lacks native UUIDv7, use a small tested implementation or suitable dependency rather than falling back to human-readable IDs.

## Write consistency
For write paths changed in 0.7, domain mutation and required audit/history belong to one SQLite transaction.

## Compatibility
Home/room navigation remains usable; explicit room relations resolve; additive room notes save/display; existing data migrates in place without re-import; no AI/Drive setup is required.

## Verification
Verify schema version, migration completion, migrated-object counts, permanent-ID presence/uniqueness, legacy mapping resolution, relation targets, Source/IngestOccurrence/InboxItem structures and preservation of notes/history.

Automated tests cover fresh bootstrap, representative 0.6.2 upgrade, migration retry/idempotency, permanent-ID uniqueness, relation preservation and atomic write/audit behavior.

## Delivery sequence
1. **0.7a — schema/migration framework + permanent IDs**
2. **0.7b — migrate existing objects/relations/notes + verification**
3. **0.7c — Source/IngestOccurrence/InboxItem persistence foundation**
4. **0.7d — atomic write/audit cleanup + release verification**

Scope does not expand without an explicit spec/decision update.

## Release gate
Do not call 0.7 complete until an upgrade test from current 0.6.2 demonstrates:

**same usable household data + preserved notes/history + stable permanent IDs + valid relations + new source-processing foundation + no dependency on AI or Drive.**
